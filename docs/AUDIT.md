# 주간 성과 점검 절차

매주 월요일 오전에 도는 예약 작업이 이 문서를 그대로 따른다. 하는 일은 하나다. Metricool에서 @yeon.virel 게시물의 성과를 읽고, `engine/audit.mjs`로 계산해 `state/audit/`에 기록한다.

**하지 않는 것**
- 게시·예약·수정·삭제. Metricool은 읽기만 한다.
- `GUIDE.md`·`engine/` 수정. 바꿀 만한 게 보이면 "제안"으로 적기만 하고, 반영 여부는 대표가 정한다.
- 다른 브랜드의 데이터를 읽는 것. brandId는 `7763847` 하나뿐이다.
- 사용자에게 질문하는 것.

방법은 instagram-agent-skill의 ig-audit 방식을 따른다(`docs/ig-agent-skill-review.md` 참고).
- 원시 조회수로 순위를 매기지 않는다. **그 네트워크 중앙값 대비 배수**와 **도달당 저장·공유**로 본다.
- 표본이 적거나 도달이 너무 작으면 결론을 내지 않는다. 스크립트가 "판단 보류"를 낸다.

## 0. 준비

저장소 최상위 폴더에서 실행한다.

```
git fetch -q origin main && git checkout -q -B main origin/main
```

## 1. 받을 지표 확인

```
node engine/audit.mjs fields
```

instagram·threads·facebook 세 네트워크의 metric id 배열이 나온다. **순서를 바꾸지 않는다.** 스크립트는 이 순서대로 읽는다.

## 2. Metricool에서 받기

`getAnalyticsDataByMetrics`를 네트워크마다 **한 번씩, 따로** 세 번 부른다. 한 요청에 섞으면 안 된다.

- `brandId`: `"7763847"`
- `from`: 오늘(한국 시각)로부터 28일 전 `00:00:00+09:00`. 그날이 2026-11-01보다 이르면 `2026-11-01T00:00:00+09:00`.
- `to`: 지금 시각 (`+09:00`)
- `metrics`: 1단계의 배열 그대로

캡션 글은 일부러 받지 않는다. 받아 적을 양을 줄이기 위해서다. 우리 게시물은 `state/posted.jsonl`의 예약 시각(±15분)으로 찾는다.
응답이 너무 커서 파일로 저장됐다고 나오면 손으로 옮기지 말고, 그 파일을 `node`나 `python3 -I`로 읽어 3단계 파일을 만든다.

## 3. 받은 그대로 저장

응답의 `rows`를 고치지 않고 `state/audit/raw/<YYYY-MM-DD>.json`에 저장한다. 날짜는 한국 시각 기준 오늘이다.

```json
{
  "fetchedAt": "<지금, ISO>",
  "from": "<2단계 from>",
  "to": "<2단계 to>",
  "instagram": [ ...instagram 응답의 rows... ],
  "threads":   [ ...threads 응답의 rows... ],
  "facebook":  [ ...facebook 응답의 rows... ]
}
```

rows는 시각·주소·숫자뿐이니 Write 도구로 그대로 옮긴다. 어느 네트워크가 오류를 내면 그 네트워크는 `[]`로 두고, 5단계 관찰에 "<네트워크> 데이터 못 받음"이라고 적는다. 바로 재시도하지 않는다.

## 4. 계산 (아직 push하지 않음)

```
node engine/audit.mjs report state/audit/raw/<YYYY-MM-DD>.json --no-push
```

생성된 `state/audit/<YYYY-MM-DD>.md`를 Read로 처음부터 끝까지 읽는다.

## 5. 관찰 쓰기

임시 파일(예: 스크래치 폴더의 `notes.md`)에 쓴다.

**판정이 "판단 보류"인 경우**
- 첫 줄: `판단 보류: <스크립트가 쓴 이유>`
- 기록할 만한 사실 **1개까지**. 표에 있는 숫자를 그대로 옮기고, 해석이나 추측은 붙이지 않는다.
  - 예: "쓰레드 조회 중앙값 56회, 인스타 도달 중앙값 4명."

**판정이 보류가 아닌 경우: 관찰 최대 3개**
- 각 관찰은 `주장 · 근거 숫자 · n · 확신(낮음/중간/높음)` 형식으로 쓴다.
- n이 5 미만인 묶음은 근거로 쓰지 않는다.
- 원시 조회수 비교는 하지 않는다. 배수와 비율만 쓴다.
- 시간대·요일은 다른 묶음(분야·표지 종류·형식)에서 아무것도 나오지 않을 때만 본다.
- "인스타 도달은 높은데 팔로우가 0"이면 내용 문제가 아니라 프로필 문제로 따로 적는다.

**제안 (선택)**
- `제안:`으로 시작하는 줄, 최대 2개. 예: "제안: 해외 분야 점수 1점 낮추기 (해외 n=8, 배수 평균 0.4x)".
- 제안만 하고 `GUIDE.md`는 고치지 않는다.

## 6. 기록하고 push

```
node engine/audit.mjs report state/audit/raw/<YYYY-MM-DD>.json --notes <notes.md 경로>
```

`state/audit/`(원자료 포함)가 main에 커밋·푸시된다. 종료 코드 3은 push 실패라는 뜻이다. 그러면 결과가 사라지지 않도록 마지막 보고에 `## 판정`과 `## 네트워크별 기준값` 부분을 그대로 붙이고, push 실패 원인을 적는다.

## 7. 알림과 보고

- PushNotification을 한 번 보낸다: `주간 점검 <날짜>: <판정 한 줄>` (보류면 보류 이유, 아니면 가장 확신 높은 관찰).
- 마지막에 같은 내용을 한 줄로 보고한다.
